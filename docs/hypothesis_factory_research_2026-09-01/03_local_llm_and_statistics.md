## PART A — Local LLM practicalities (September 2026)

### A1. The actual hardware (measured on this machine)

`sysctl`: **Apple M5, 10-core CPU, 16 GB unified memory**. M5 specifics: **153 GB/s memory bandwidth** (~30% over M4's 120 GB/s) and GPU Neural Accelerators that dramatically speed prefill ([Apple newsroom](https://www.apple.com/newsroom/2025/10/apple-unleashes-m5-the-next-big-leap-in-ai-performance-for-apple-silicon/)). Measured MLX impact on M5 vs M4 for Qwen3-14B-4bit: **4.06× faster time-to-first-token, 1.19× faster generation** ([yage.ai MLX vs llama.cpp analysis](https://yage.ai/share/mlx-apple-silicon-en-20260331.html)).

**16 GB is the binding constraint, not the 10 cores.** macOS lets the GPU wire only ~70% of unified memory (~11 GB usable; raisable via `sysctl iogpu.wired_limit_mb` at your own risk) ([Local AI Master 16GB Mac guide](https://localaimaster.com/mac/best-llm-16gb-mac)). Practical ceiling: **dense ~14B at Q4 (tight) or ~9–12B comfortably**. The popular MoE sweet spot (Qwen3.5/3.6-35B-A3B, ~130 tok/s on big Macs) does **not** fit at Q4 (~20 GB weights); `--cpu-moe` offload exists but kills the speed advantage ([InsiderLLM function-calling guide](https://insiderllm.com/guides/function-calling-local-llms/)).

Expected decode speeds on this M5 (bandwidth-bound: ≈153 GB/s ÷ weight bytes touched):
- 8–9B Q4 (~5–6 GB): **~30–40 tok/s** (Llama-3.1-8B Q4 measured ~33 tok/s on base M4; M5 ~1.2× faster)
- 12B Q4 (~7 GB): **~20–28 tok/s** — this is the already-configured Gemma4-12B-QAT class
- 14B Q4 (~9 GB): **~15–20 tok/s**, MLX ~2× llama.cpp on dense 14B (38 vs 18 tok/s on M4-class) ([Markaicode M4 benchmark](https://markaicode.com/benchmarks/hugging-face-qwen-3-m4-max-throughput-benchmark/))
- A 1,400-token proposal (the loop's current cap): **~1–1.5 min/hypothesis** on the 12B; **hundreds of proposals/day are free**.

### A2. Model menu for this box (Sept 2026)

Current line-up per [SitePoint 2026 comparison](https://www.sitepoint.com/best-local-llm-models-2026/), [Atomic Chat 16GB guide](https://atomic.chat/blog/guides/best-local-llm-16gb-mac), [InsiderLLM](https://insiderllm.com/guides/function-calling-local-llms/):

- **Qwen3-14B / Qwen3.5 14B-class at Q4** — quality ceiling for this RAM; tight squeeze.
- **DeepSeek-R1-0528-Qwen3-8B** — best open ~8B reasoner (leads AIME among open 8Bs, fits 8 GB) ([PromptQuorum](https://www.promptquorum.com/local-llms/best-local-reasoning-model-deepseek-r1-2026)). The original R1 distills (Qwen2.5-based, Jan 2025) are effectively superseded by this and by Qwen3.5 natives.
- **Gemma4 12B QAT** — already configured in the loop; fine as the cheap mutation engine. Gemma 4 26B-A4B (~15 GB) is borderline — would need every trick and leaves no headroom for the Rust build + caches.
- **Llama 4**: not competitive at this size class in practice; community consensus favors Qwen/Gemma/DeepSeek for ≤16 GB. **Mistral Small 3 (24B)**: Q4 ≈ 14 GB — doesn't coexist with anything else on a 16 GB box.

### A3. Runtime choice

- **MLX is now the default answer on Apple Silicon**: Ollama v0.19 (Mar 2026) added an MLX backend precisely because of M5 Neural Accelerators; MLX advantage is ~1.4–1.8× over raw llama.cpp on dense models, up to 3× headline on MoE, plus ~13% lower memory ([yage.ai](https://yage.ai/share/mlx-apple-silicon-en-20260331.html), [Ante Kapetanovic benchmark](https://antekapetanovic.com/blog/qwen3.5-apple-silicon-benchmark/)). Ollama's Go wrapper historically ate ~50% of llama.cpp throughput — avoid old Ollama versions.
- **LM Studio (already integrated) supports both MLX and GGUF engines** — the existing `LmStudioClient` needs zero code changes to benefit; just load an MLX build of the chosen model. This is the lowest-friction path.
- KV-cache: keep **Q8 or higher KV cache for tool/JSON work** — aggressive KV quant degrades schema tracking ([InsiderLLM](https://insiderllm.com/guides/function-calling-local-llms/)).

### A4. Tool-calling / JSON-schema reliability of local models

- **Syntactic validity is a solved problem**: grammar-constrained decoding (llama.cpp GBNF, LM Studio/OpenAI-compat `response_format: json_schema strict`, Outlines) **guarantees** schema-valid JSON. The loop already uses strict json_schema — correct design.
- **Semantic validity is not**: `{"temperature": 999}` is valid JSON with a nonsense value; validate argument values independently ([InsiderLLM](https://insiderllm.com/guides/function-calling-local-llms/)). [JSONSchemaBench (ICLR 2025)](https://qaskills.sh/blog/bfcl-berkeley-function-calling-leaderboard-guide-2026) found 3–41% coverage on the hardest real-world schemas across constrained-decoding frameworks; [NESTFUL](https://qaskills.sh/blog/bfcl-berkeley-function-calling-leaderboard-guide-2026) measured even GPT-4o at 28% on nested call sequences.
- On [BFCL V4](https://gorilla.cs.berkeley.edu/leaderboard.html), small open models trail frontier models materially on multi-turn/agentic categories; a stark community datapoint: Qwen3-coder-class scored **6.75% first-try** on a complex real-world API-shape task, recovered to ~100% only with a validation-feedback retry harness ([typia/samchon writeup](https://typia.io/blog/function-calling-harness-qwen-meetup-korea/)). Lesson: **local models need a validate-and-retry loop around every structured call** (schema check → semantic lint → one retry with the error message). Keep schemas flat: enum-typed mechanism families + numeric parameter dicts, never nested unions.
- **Implication for the factory**: local models are reliable enough to *fill pre-defined hypothesis templates* (pick family, jitter parameters, justify in one paragraph) and unreliable for *free-form Rust codegen*. Keep the DSL-style proposal schema; never let the local model emit code — the coordinator's existing fail-closed design already assumes this.

## PART B — Statistical discipline for an automated search

### B1. The inflation you must beat, in this project's units

- Sharpe-world benchmark: after 1,000 independent backtests the **expected maximum Sharpe is 3.26 even when every true SR = 0** ([Bailey & López de Prado, Deflated Sharpe Ratio, SSRN 2460551](https://ssrn.com/abstract=2460551); [PDF](https://www.davidhbailey.com/dhbpapers/deflated-sharpe.pdf)).
- **Win-rate translation for this project** (break-even ≈ 0.85, fresh-gate support n = 110): SE = √(0.85·0.15/110) ≈ 0.034. Expected max excess win-rate over break-even among N null candidates ≈ SE·√(2 ln N): **N=20 → +0.083; N=100 → +0.103; N=500 → +0.120**. The current single-candidate gate needs point-estimate ≈ BE + 1.96·SE + 0.02 ≈ +0.087 to pass. **So ~20 independent null candidates evaluated against one n=110 fresh window are already expected to produce one false pass; at N=100 a false pass is near-certain.** A machine generating hundreds of candidates cannot reuse the single-candidate gate.

### B2. Toolbox, ranked by fit

1. **Family-wise correction inside each consumed window (simplest, do first).** If K candidates touch one fresh window, replace z=1.96 with the Šidák/Bonferroni z for α=0.05/K: **K=5 → z=2.57; K=10 → 2.81; K=20 → 3.02; K=50 → 3.29**. Equivalently keep z=1.96 and raise the Wilson margin by (z_K−1.96)·SE. Cross-checked against the repo's own power table: at n≈110 you only have power for edges ≥0.10 even at K=1, so **cap K per consumed window at ~3–5** or power collapses entirely.
2. **False Discovery Rate (Benjamini–Hochberg) across the candidate batch** — the right tool for the *screening* stages where you want discoveries per unit data, not certainty: rank the batch's p-values (from Wilson z-scores vs break-even), pass the largest set with p_(i) ≤ q·i/N at **q = 0.10**. FDR control for strategy selection is the Harvey–Liu program ([Harvey & Liu; see also Benjamini-Hochberg/Storey lineage in data-snooping literature](https://www.efmaefm.org/0EFMAMEETINGS/EFMA%20ANNUAL%20MEETINGS/2020-Dublin/papers/EFMA%202020_stage-1301_question-Full%20Paper_id-114.pdf)); Harvey–Liu's cross-sectional conclusion — a **t-hurdle of ≈3.0, not 2.0**, for any newly discovered effect — is a good permanent floor for the *final* promotion stage.
3. **White's Reality Check / Hansen's SPA on the shared historic window** — bootstrap the *entire family* of candidates jointly (stationary bootstrap of daily blocks over the distilled-candle window), ask "does the best candidate beat break-even after accounting for having searched the family?" ([White 2000 RC; Hansen 2005 SPA; Hsu–Kuan application to technical rules](https://papers.ssrn.com/sol3/papers.cfm?abstract_id=685361); [Corradi–Swanson survey](https://econweb.rutgers.edu/nswanson/papers/corradi_swanson_whitefest_1108_2011_09_06.pdf); [Step-SPA for identifying *which* rules](https://homepage.ntu.edu.tw/~ckuan/pdf/Step-SPA-20090720.pdf)). RC is conservative when many junk candidates dilute the family (exactly a hypothesis factory's failure mode) — use **SPA**, which studentizes and discards hopeless candidates. Practical: the factory logs every candidate evaluated per window (it already snapshots evidence); SPA needs that full trial ledger — **never delete losing trials, they are the null distribution.**
4. **Deflated Sharpe Ratio / expected-max deflation** for any Sharpe-like metric: benchmark SR₀ = √V[SR trials]·((1−γ)Φ⁻¹(1−1/N) + γΦ⁻¹(1−1/(Ne))), γ≈0.5772, then DSR = prob(SR > SR₀ given T, skew, kurtosis) ([Bailey & López de Prado](https://ssrn.com/abstract=2460551); [Quantdare walkthrough](https://quantdare.com/deflated-sharpe-ratio-how-to-avoid-been-fooled-by-randomness/); [Wikipedia](https://en.wikipedia.org/wiki/Deflated_sharpe_ratio)). Use **N = effective independent trials** (cluster candidates by parameter-correlation; a 50-variant jitter of one band is ~3–8 effective trials, not 50).
5. **CPCV / PBO for the discovery stage**: Combinatorial Purged CV turns one equity curve into a distribution of OOS paths and yields the **Probability of Backtest Overfitting** via CSCV (rank the IS-best candidate's OOS rank; PBO = fraction of splits where IS-best is below-median OOS). Controlled synthetic comparisons show CPCV strictly dominates plain walk-forward on false-discovery prevention ([Knowledge-Based Systems 2024 comparison](https://www.sciencedirect.com/science/article/abs/pii/S0950705124011110); [López de Prado purged CV](https://en.wikipedia.org/wiki/Purged_cross-validation); [QuantInsti explainer](https://blog.quantinsti.com/cross-validation-embargo-purging-combinatorial/); scikit-compatible implementation: [eslazarev/purged-cross-validation](https://github.com/eslazarev/purged-cross-validation)). **Purging/embargo sizing for 5m candle markets**: labels resolve at window close, so label overlap is nil; the real dependence is regime clustering — use **day-level blocks** (288 windows/block) for CV folds and bootstrap, with a 1-day embargo between discovery and validation folds. Add PBO ≤ 0.2 as a screen-stage gate.
6. **Anytime-valid sequential gates (e-values / confidence sequences) — the best match for a continuously running factory with streaming fresh data.** An e-process for Bernoulli win-rate vs break-even (test-martingale / betting form: E_t = Π (1 + λ(X_i − p_BE)) with mixture over λ) lets the live loop **monitor a candidate continuously and stop the moment evidence suffices, with exact type-I control at any data-driven stopping time** — no preregistered n, no burned window on early stopping ([Ramdas et al., SAVI/game-theoretic statistics, ICML 2025 tutorial](https://icml.cc/virtual/2025/40002); [e-values overview](https://en.wikipedia.org/wiki/E-values); [anytime-valid tests ≡ adaptive designs, 2026](https://arxiv.org/pdf/2606.00878); ["Anytime validity is free", JRSS-B 2026](https://academic.oup.com/jrsssb/advance-article/doi/10.1093/jrsssb/qkag050/8493290)). Bonus: **e-values multiply across independent windows and support FDR via e-BH**, giving a clean "test-budget ledger": each candidate carries a running e-value; promote at E ≥ 20 (≈α=0.05), kill at E ≤ 0.1. This directly fixes the power problem documented in `wilson_gate_power_analysis`: an edge-0.15 candidate promotes in ~30–70 fills, an edge-0.05 one keeps accumulating across consecutive fresh windows instead of dying at an arbitrary n=110 snapshot.

### B3. Test-budget accounting (the part most factories skip)

- Principle: **a historic window's alpha is a depletable resource; fresh windows are income.** Every candidate evaluated against a window burns power for all future tests on that window (max-statistic inflation grows √(2 ln N)).
- Concrete ledger, sized for this project (~8,600 windows/mo; band-entry flow ≈ 40–60 signals/day on the public instrument given SUPPORT_MIN=110 accrued in ~2 days):
  - **Historic discovery slab** (distilled cache, unlimited re-reads): unlimited Tier-0 exploration, but every trial logged with candidate-hash → the trial count N feeds SPA/DSR/e-BH at the next stage. This slab is *never* promotion evidence.
  - **Holdout slab** (fixed, older): ≤ 1 batch query/week, BH q=0.10 across the batch; a candidate may touch it **once per lifetime** (re-touch = new candidate ID with a parent link, inflating its family N).
  - **Fresh slab** (post-freeze, one-shot CONSUMED markers — already implemented): ≤ 3–5 candidates per consumed gate, Šidák-adjusted z, or replace with per-candidate e-processes over streaming resolutions (then no batching needed; the budget is enforced by e-BH across concurrently monitored candidates — cap concurrent monitors at ~10).
  - **Preregistration contract (machine version of what you already do by hand)**: before any outcome-bearing read, the coordinator writes `{candidate_id, family, parent_id, exact rule, entry window, gate statistic, α-spend, N_family_to_date, data window hash}` to the registry and commits the hash. The existing `fresh_gate_public_v1.py` marker-before-outcome-read pattern is exactly right — generalize it to every candidate.
  - **Kill-reason memory**: rejected families are negative prompt examples (AlphaMemo/AlphaAgent pattern) so the generator stops resampling the 15+ dead families — this is *power conservation*, not just efficiency.
- **One live slot** changes the objective: this is best-arm identification, not hypothesis testing of everything. Use confidence-sequence racing (successive elimination): challengers race in `bounded_vps_shadow` (stage already exists); a challenger displaces the champion only when its lower confidence bound exceeds the champion's upper bound on overlapping windows. Champion stays deployed throughout — no exploration cost on the bankroll.

### B4. Recipe summary (numbers to adopt)

1. Fix the power mismatch first: margin m=0 with z chosen by family size (per repo's own analysis, m=+0.02 at n≤110 is unreachable below edge≈0.15); or move gates to e-processes entirely.
2. Tier-0 local generator: unlimited, logged; Tier-1 screens: BH q=0.10 + PBO≤0.2 (day-blocked CPCV, S=8–16 splits); Tier-2 SPA test across the season's full trial ledger before any candidate reaches fresh data.
3. Fresh-data promotion: ≤5 candidates per consumed window at z=2.57, or ≤10 concurrent e-process monitors with promote@E≥20 / kill@E≤0.1, e-BH across monitors.
4. Final promotion floor: Harvey–Liu-style t≈3 equivalent (z≥3 on the pooled fresh evidence), plus fixed-forward confirmation (stage exists) plus human sign-off for the one live slot.
5. LLM stack: keep LM Studio + strict JSON schema (exists); load Qwen3.5-9B or keep Gemma4-12B as MLX build (M5: ~20–40 tok/s decode, 4× prefill vs M4); add validate-retry harness; Sonnet 5 Batch nightly re-rank (~$1–5/night); weekly Claude Code deep pass on Max plan ($100–200/mo flat). Never let any LLM write to the gate path — the coordinator's fail-closed design already enforces this.
